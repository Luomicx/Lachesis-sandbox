# Lachesis 仿真引擎设计

## 1. 设计原则

Lachesis 使用混合仿真，而不是把人生选择交给自由对话的 LLM Agent。

- `Mesa` 管理世界、Agent、状态、网格/网络和重复实验。
- `SimPy` 管理按月或按事件触发的流程、延迟、容量与资源竞争。
- 领域规则负责录取、学习、求职、绩效、晋升、现金流和状态迁移。
- LLM 只提供角色的受限决策建议、事件叙述、解释和对话；输出经 schema 校验后才可成为候选事件。
- 生涯建模官独立于世界角色，只负责导入资料解析、缺失信息追问和结构化档案确认；不得访问或扮演未来世界中的角色。

## 2. 分层架构

```text
Case / Scenario Version
  -> Evidence & Assumption Registry
  -> Mesa CareerWorld
       -> Person, Relationship, Organization, Market Agents
       -> State Store and Rule Evaluator
  -> SimPy Event Processes
       -> Exam, Degree, Recruiting, Employment, Shock Processes
  -> Run Ledger
       -> Snapshots, events, random seed, outcomes
  -> Aggregator / Report Agent / Future World UI
```

## 3. 世界状态

每个世界 `W` 在时点 `t` 包含：

```text
W(t) = [P, R, O, M, C, E]
P: 个人状态      R: 关系网络      O: 组织/学校状态
M: 行业和地区环境 C: 约束与资源    E: 已发生事件
```

个人状态至少包含技能向量、教育信号、经验、现金流、精力、满意度、压力、求职状态、当前组织和长期目标进度。关系网络包含匿名的家人、朋友、导师、同学、同事和直属老板等角色。每个世界第一版控制在“个人分身 + 3-5 个关系/职场角色 + 1 个行业环境 Agent”。任何结论性指标必须由规则计算，不得仅由自然语言总结得出。

## 4. Agent 类型

| Agent | 责任 | 是否由 LLM 驱动 |
| --- | --- | --- |
| PersonAgent | 执行学习、申请、工作、跳槽和资源分配策略 | 可选，受策略/预算约束 |
| PersonaVariantAgent | 同一用户的稳健、成长、平衡等策略分身 | 可选 |
| MentorAgent | 影响指导、推荐、研究/项目机会 | 是，输出候选影响 |
| ManagerAgent | 影响绩效反馈、项目机会和晋升推荐 | 是，输出候选影响 |
| OrganizationAgent | 处理岗位容量、薪酬带、绩效制度和组织风险 | 否，规则优先 |
| SchoolAgent | 处理项目质量、导师/实验室机会和毕业要求 | 否，规则优先 |
| MarketAgent | 行业需求、薪资带、招聘窗口和宏观冲击 | 否，数据/规则优先 |

关系 Agent 产生的影响必须经过规则校验并限制在机会概率或关系状态范围内，例如导师支持提高实习邀约概率、经理反馈提高项目分配概率。它们不得直接写入录取、升职、收入或其他结论性结果。

## 5. SimPy 事件过程

### 5.1 教育路径

`ExamPreparationProcess` 消耗时间、精力和现金；按用户基础、投入、专业竞争度和随机扰动产生分数区间。`AdmissionProcess` 将成绩映射为录取结果，但必须把学校层级、专业、名额、地区与调剂/回退策略分开建模。`DegreeProcess` 每月生成课程、项目、导师互动、实习和毕业事件。

### 5.2 工作路径

`JobSearchProcess` 处理投递、面试、Offer、拒绝和空窗期。`EmploymentProcess` 处理项目、技能增长、绩效、加薪、晋升、裁员和跳槽窗口。岗位机会由 MarketAgent 与 OrganizationAgent 的容量共同约束。

### 5.3 冲击与生活约束

`ShockProcess` 按情景概率产生行业下行、组织重组、家庭责任变化或健康负荷事件。冲击不应只产生负面结果，也要允许意外项目、导师推荐和市场上行等正向事件。

## 6. 情景、随机性与分叉

一个 `ScenarioVersion` 由基线版本、干预列表、规则版本和证据版本唯一确定。每个世界运行使用一个独立随机种子。用户只能选择 1 年、3 年、5 年的时间跨度；前 12 个月使用月度时钟，之后使用季度时钟。每条路径默认运行 20 个世界，允许快速预演 10 个或深入预演 50 个，禁止任意指定运行数量。

```text
Baseline v1 + {school_tier = key, city = Shanghai}
  -> Scenario v2
  -> seed 101..150
  -> 50 个可比较的 WorldRun
```

变量注入只能改变可控前因，例如接受 Offer、目标学校/专业、培训、实习、学习投入、跳槽或城市选择。系统从最近快照恢复，并仅重算受影响的未来事件；不得直接覆写录取、升职或收入等结果。基线的历史、日志和报告永不覆盖。

## 7. 结果计算

每个指标保留原始值和标准分。建议使用以下结果而不是单总分：

- 分布：中位数、P10/P90、达到阈值的概率；录取概率、收入与职业发展速度须明确标为模拟区间。
- 对比：路径 A 与 B 的差值分布和优势概率。
- 可逆性：在何时、以何代价可切换到另一条路径。
- 敏感性：逐一扰动关键变量，识别会使结论反转的阈值。
- 归因：每项变化关联到输入、规则、事件和随机扰动类别。

总效用仅作为用户自定义的排序视图：

```text
U = sum(weight_i * normalized_metric_i) - irreversible_risk_penalty
```

MVP 不提供总效用、路径排序或推荐算法。指标权重仅用于用户查看单个指标的聚合方式，不能生成“最佳路径”结论。

## 8. LLM 边界与防护

1. 所有 LLM 输出使用 JSON Schema，包含提议事件、理由、证据引用和置信度。
2. 规则校验器检查事件是否违反资源、时间、资格、概率或现实约束。
3. 缓存模型输出，记录模型、提示词模板、温度和输入摘要，保证运行可复核。
4. LLM 不可读取其他世界的未来结果，避免时间线泄漏。
5. 角色对话只能检索当前世界截至当前时点的事件和记忆。
6. 自动生成的关系角色无需在首次运行前由用户逐一确认；用户资料不足时，角色应降低影响权重并在报告中标记为模型假设。
7. 世界角色只接收最小化派生属性，不能读取原始附件、具体家庭描述或敏感资料原文。
8. LLM 提议事件必须映射到已有规则、用户输入或证据并通过结构化校验；未通过校验的内容只能保留为叙事，不能写入世界状态或指标。

## 9. 校准与验证

- 单元验证：学历、经验、现金流和状态转移规则。
- 属性验证：资金不能无故增长；未满足前置条件不能进入下一状态；相同种子可复现。
- 回放验证：用匿名历史案例检查模型是否能生成合理的已知路径范围，不以“准确预测个人命运”为指标。
- 专家校准：职业咨询、招生、行业从业者审查规则和默认假设。
- 偏差审计：不同背景下检查模型是否因代理变量产生不合理的机会差异。
- 数据审计：每项官方招生或录取数据记录官网链接、发布日期、适用年份、上传者、审核状态和数据版本；用户上传的数据只影响该用户案例，不能作为全局事实写入。
- 数据来源：首版不做实时全网爬取。所有官方数据即使带有官网链接，也必须经运营人员人工审核，才能从案例数据升级为全局默认数据。
- 缺失数据处理：当官方数据不能支持具体学校、专业和用户画像的量化估计时，结果必须返回 `insufficient_data`，不得生成伪精确的录取概率。
- 数据目录范围：首版全局默认数据集仅包含 20 个计算机相关研究生项目和 6 个核心就业城市。超出目录的项目或城市不得复用近似数据作为量化依据。
- 目录治理：项目和城市目录仅由运营人员配置并版本化；运行记录引用具体目录版本，用户不可将目录外对象请求为量化概率目标。
